# Report publication custody

Status: local implementation candidate; not deployed and not production
cleanup authority.

`generate_report` serializes supported publishers with a nonblocking advisory
lock in the report parent. The lock is acquired before staging creation and
held through generation, publication, and bounded cleanup. A second supported
publisher refuses rather than waiting or treating an interrupted layout as a
stable one.

The publisher creates `.report-tmp-<uuid>` exclusively, immediately opens it
as a no-follow directory, and retains that descriptor and identity. Ordinary
generation failure clears generated bytes through the retained descriptor and
leaves the empty directory root. Pathname replacement after descriptor capture
cannot redirect that cleanup to the replacement. Publication verifies the
held descriptor and pathname identity, then records `COMMIT_STARTED` before
the first rename. Once that state is reached, generic failure cleanup does not
delete any stage, live, `.prev`, or recovery object.

The supported concurrency contract requires every Labelwatch report publisher
for the enrolled destination to honor the sibling lock. It excludes a
non-cooperating process with the same UID mutating the parent namespace during
the irreducible `mkdir` to first `open` interval; Python's `mkdir` does not
return an identity-bearing descriptor. This assumption is explicit rather
than claimed as mechanically observed. Removing it requires a different
directory-custody mechanism and is not established by this patch.

Forward renames check the expected source identity before and after the move.
On disagreement the operation refuses and retains the resulting objects for
explicit reconciliation. It does not attempt an automatic reverse rename:
ordinary `os.replace` cannot guarantee that reversal will not overwrite a
pathname created concurrently. A missing live tree with present `.prev` is
therefore an ambiguous interrupted layout and refuses before generation.

After a successful live replacement, `out_dir.prev` is the immediate rollback
tree. Only the older rollback, already moved under its unique recovery name,
is eligible for byte clearing. Clearing uses an identity-bound no-follow
descriptor and retains its empty root. Substitution or a cleanup error leaves
the recovery object and reports `COMPLETE_WITH_RETAINED_RECOVERY`; it never
weakens the installed live tree or immediate rollback custody.

This change does not automatically reconcile historical `.report-tmp-*`
directories, delete production artifacts, deploy a release, or establish
crash/filesystem durability. Existing historical inventory remains evidence;
any production cleanup requires separate exact identity and authority.
